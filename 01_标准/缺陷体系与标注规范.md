# 缺陷体系与标注规范（v0.3 草案）

> 面向「AI 生成 PPT 的多层次质量审查与风险优化智能体」
> 文档定位：项目**接口契约**。缺陷类别表、检测分工、记录结构、标注口径四者一旦确定，融合层、报告层、实验设计都以此为准。
> 状态：v0.3。变更仅涉及**路由与定位**，未新增或删除任何缺陷编码，`Finding` 结构未变：
> - v0.1 → v0.2：`S-DECO-COUNT` 提至首批（首批 8 类 → 9 类）
> - v0.2 → v0.3：原则一修正为"编码按现象族、路由按证据可得性"（两者解耦）；`V-HIERARCHY` 判定依据由"字号/面积/对比度比值不足"改为"字号比纯测量"，首选层 L2 → L1；风格指标拆为 PTPS（页内）与 HCI（页间），取消实验四
>
> 参数仍为初始默认值，须经实验一校准后方可冻结。

---

## 1. 为什么先做这份文档

项目里有三个创新点、四个数据集、五个实验。如果缺陷类别和记录结构不先定死，会出现三种必然的返工：

1. 规则检测器输出的字段和机器学习检测器不一致，融合层只能靠字符串匹配硬凑。
2. 标注做到一半发现某一类缺陷无法用统一结构描述，整批标注作废。
3. 实验二做方案对比时，才发现各方案覆盖的缺陷类别不同，指标不可比。

因此本文档的产出优先级高于任何代码与界面。

---

## 2. 三条设计原则

**原则一：编码按现象族分，路由按证据可得性定，两者解耦。**
"文字溢出"和"跨页数据矛盾"在用户眼里都是"这页有问题"，但前者只需读 PPTX 的 XML，后者必须理解语义。因此编码以**用户可理解的缺陷类型**命名（`S-` 结构 / `V-` 视觉 / `M-` 语义 / `R-` 要求），供报告组织与用户阅读；**由哪个检测层执行，由 3.2 表"首选层"字段决定**。

两者通常一致，但允许例外：`V-HIERARCHY`（视觉层次）的最小证据是字号属性，不需要渲染图，故路由到 L1 规则层。这类例外的合法性由**证据可得性**判定，不由现象归属判定。

> v0.3 修正：v0.1 的表述是"按证据可得性分类"，隐含"前缀即路由"。遇到"视觉现象但结构属性可判"的混合情况时该假设自相矛盾，故改为解耦。实现时以 `preferred_layer` 字段为准，不要用 `code[0]` 推断。

**原则二：一条缺陷可以有多个检测器，但只能有一个编码。**
编码描述"是什么问题"，`detector` 描述"谁发现的"。同一编码的多条记录进入融合簇，这才是去重和交叉验证的对象。

**原则三：不确定必须是一等公民。**
每条记录必须能表达"我不确定"。系统允许弃权（`needs_review`），但弃权率要计入实验指标，否则可以通过大量弃权刷高精确率。

## 3. 缺陷体系

### 3.1 证据族

| 前缀 | 证据族 | 判定所需的最小证据 | 典型检测层 |
|---|---|---|---|
| `S-` | 结构 Structural | PPTX 对象的几何、属性、层级关系 | L1 确定性规则 |
| `V-` | 视觉 Visual | 页面渲染图像的统计特征 | L2 传统机器学习 |
| `M-` | 语义 Meaning | 文本含义、图文关系、跨页逻辑 | L3 多模态大模型 |
| `R-` | 要求 Requirement | 用户原始 Prompt / 参考资料与结果的比对 | L3（需 Prompt） |

`R-` 族是横切的：它本身不描述视觉现象，而是描述"是否满足用户提出的条件"。缺少 Prompt 时，`R-` 族**整体不可用**，系统必须显式声明"未核验原始要求"，而不是静默跳过。

### 3.2 缺陷类别表

批次说明：**首批**＝最低交付必须实现；**二批**＝有余力再做；**观察**＝只做探索性分析，不进主实验。

| 编码 | 名称 | 族 | 判定依据 | 首选层 | 批次 | AI 高发 |
|---|---|---|---|---|---|---|
| `S-OVERSHOOT` | 元素越界 | S | 对象 bbox 超出页面边界 | L1 | 首批 | 通用 |
| `S-TEXT-OVERFLOW` | 文字溢出 | S | 自动缩放失效，实测文本高 > 框高 | L1 | 首批 | **是** |
| `S-FONT-FALLBACK` | 字体替换 | S | 指定字体在当前渲染环境不可用 | L1 | 首批 | 通用 |
| `S-PAGECOUNT` | 页数超限 | S | 实际页数 > 用户指定上限 | L1 | 首批 | 通用 |
| `S-EMPTY` | 空页 / 残页 | S | 有效前景面积或字数低于阈值 | L1 | 二批 | **是** |
| `S-DENSITY` | 单页过密 | S | 字数、行数或对象数超阈值 | L1 | 二批 | 通用 |
| `S-DECO-COUNT` | 装饰元素过量 | S | emoji 与纯装饰 shape 计数超阈值 | L1 | 首批 | **是** |
| `V-WHITESPACE` | 留白失衡 | V | 四边留白极差或单边占比异常 | L2 | 首批 | 通用 |
| `V-ALIGN` | 对齐断裂 | V | 同类元素边缘或间距方差异常 | L2 | 二批 | 通用 |
| `V-HIERARCHY` | 视觉层次弱 | V | 标题/正文字号比低于阈值（纯属性测量，不做审美判断） | L1 | 二批 | **是** |
| `V-COLOR` | 配色漂移 | V | 页间主色分布距离超阈值 | L2 | 二批 | 通用 |
| `V-TEMPLATE-REPEAT` | 布局模板化 | V | 相邻页布局特征余弦相似度超阈值且连续 | L2 | 首批 | **是** |
| `M-CROSSPAGE` | 跨页不一致 | M | 同一数据、术语或结论在不同页矛盾 | L3 | 首批 | **是** |
| `M-IMAGE-TEXT` | 图文不符 | M | 配图与页面文字主题关联弱 | L3 | 二批 | **是** |
| `M-DECO-FUNC` | 装饰无信息功能 | M | 元素不承担信息表达作用 | L3 | 二批 | **是** |
| `R-CONTENT-MISS` | 要求内容缺失 | R | 已拆解条件未满足 | L3 | 首批 | 通用 |
| `R-STYLE-DEVIATE` | 风格偏离要求 | R | 配色、字体或风格与要求不符 | L3 | 二批 | 通用 |
| `R-SCOPE` | 篇幅 / 场景不匹配 | R | 页数、文字量与汇报场景或时长不匹配 | L3 | 观察 | 通用 |

首批共 9 类，`S/V/M/R` 四族齐全，保证实验二的「方案 × 类别」矩阵不是空表。

> v0.2 变更：`S-DECO-COUNT` 由二批提至首批。原因见 `04_产品/产品形态与交互设计.md` 第 8.1 节——用户明确要求检查装饰图标，且该类为 PTPS 中 `D`（装饰密度）分项的直接来源，实现成本仅约 2 小时。
> 但**首批 ≠ 进主实验**：9 类中仅 `S-OVERSHOOT`、`V-WHITESPACE`、`M-CROSSPAGE` 三类完成标注与对照实验，其余 6 类为"实现并运行"，报告中须严格区分措辞。

### 3.3 初始阈值（待实验一校准）

以下参数为**工程默认值**，全部必须可配置、必须随记录版本号存档。未经校准前，文档与报告不得把这些数值表述为"最优"。

| 参数 | 默认值 | 说明 |
|---|---|---|
| 越界容差 | max(0.5% 页宽, 2pt) | 阴影与描边常见溢出，小于容差不计 |
| 文字溢出判定 | 文本实测高 > 框高 × 1.05 | 需先确认 autofit 关闭 |
| 字体检查范围 | 主题字体 + 显式指定字体 | 渲染前预检 |
| 留白失衡 | 四边极差 > 15% 页宽 或 单边 > 30% | 视觉族 |
| 模板化相似度 | 余弦 > 0.92 且连续 ≥ 3 页 | 需在实验一验证阈值敏感性 |
| 单页字数上限 | 按场景配置 | 汇报与阅读型差异大，不设全局值 |

## 4. 检测分工矩阵

矩阵回答一个问题：**同一份 PPT，哪些问题根本不需要调用大模型。**

| 缺陷族 | L1 规则 | L2 传统 ML | L3 多模态 | 备注 |
|---|---|---|---|---|
| `S-` 结构族 | 主责 | 不参与 | 复核争议 | 规则可给出确定结论，ML 无增益 |
| `V-` 视觉族 | 部分（可数指标） | **主责** | 复核争议 | 阈值类可先由规则初筛，ML 处理模糊区；`V-HIERARCHY` 属此类，直接走 L1 |
| `M-` 语义族 | 不参与 | 不参与 | 主责 | 无结构或统计捷径 |
| `R-` 要求族 | 部分（页数、字号） | 不参与 | 主责 | 可机检条件优先走规则 |

这张矩阵同时是**成本论证的骨架**：只要证明 `S-` 族占实际缺陷总量的比例可观，就说明"全部交给大模型"是不经济的。该比例需在实验五中用真实样本统计，不得先验假定。

## 5. AI 味检测的可分解性（项目特色，也是最易被质疑处）

审阅者最可能问的一句是：**"你怎么证明这套东西不是在用大模型猜审美？"** 回答的关键是把"AI 味"拆到不同层，而不是整体打分。

| 现象 | 可由 L1 / L2 低成本回答的部分 | 必须由 L3 回答的部分 |
|---|---|---|
| 布局模板化 | 布局特征向量相似度、连续重复页数、元素类型分布 | 这种重复对该汇报场景是否恰当（系列页本就应一致） |
| 装饰元素冗余 | emoji 与装饰 shape 的计数、面积占比 | 该元素是否承担信息功能 |
| 视觉层次 | 字号比、面积比、前景背景对比度 | 该层次是否匹配汇报类型与受众 |

据此可以给出一个**可检验的命题**：AI 味的三类现象中，大部分可被 L1/L2 覆盖，L3 只负责"是否恰当"的价值判断。

> 该命题在课程周期内**不做实证检验**（原计划的实验四已取消），仅作为设计依据记录在案。报告中不得表述为"已证实"，只能写"按此假设设计"。

同时必须守住原有边界：系统**不判定 PPT 是否由 AI 生成**，不使用任何"AI 生成概率"表述。上述现象在人工设计的 PPT 中同样可能出现。

> 面向用户的呈现口径见 `04_产品/产品形态与交互设计.md` 第 4 节：布局模板化与装饰冗余被拆为两个指标——**PTPS**（页内：对齐规整度 A、类型单调度 T、装饰密度 D）与 **HCI**（页间：相邻重复、全局重复、版式多样性）。二者共同回答"这份 PPT 有多像它自己"，属内部自相似度量，不需要 AI/人工基线，因此不构成来源判定。界面文案禁用"率""概率""检测出 AI"。
>
> v0.3 决定：两个指标**都不含"视觉层次"**。该项在三者中主观性最强，需要人工标注与一致性检验才能支撑；它已由 `V-HIERARCHY` 以"字号比测量"的形式独立呈现，不必再折进指标。相应地，实验四（指标效度检验）取消。
>
> v0.3 同时修正了 v0.2 的一处重叠：v0.1/v0.2 的 HCI 同时含页内装饰密度与页间重复，与 PTPS 重复计数。现装饰密度只归 PTPS，HCI 只保留页间量。

## 6. 统一记录结构

### 6.1 字段定义

一条记录称为 `Finding`，是系统内唯一的"结论原子"。所有检测器输出、融合、报告、实验统计都基于它。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `finding_id` | string | 是 | 全局唯一，建议 `{code}-{slide}-{seq}` |
| `slide_index` | int | 是 | 从 1 开始 |
| `defect_code` | string | 是 | 3.2 表中的编码 |
| `detector` | string | 是 | 产生该记录的检测器标识，如 `rule.geometry@0.1` |
| `severity` | enum | 是 | `blocking` / `major` / `minor` / `info` |
| `status` | enum | 是 | `confirmed` / `probable` / `needs_review` |
| `confidence` | float | 是 | 0–1，语义随 `confidence_source` 变化 |
| `confidence_source` | enum | 是 | `rule` / `model_prob` / `llm_report` / `fused` |
| `bbox` | float[4] | 否 | 归一化 `[x, y, w, h]`，页级缺陷为空 |
| `element_ids` | string[] | 否 | 关联的 PPTX 对象 id |
| `evidence` | Evidence[] | 是 | 至少一条，空证据记录不允许存在 |
| `rationale` | string | 是 | 面向用户的一句话解释 |
| `suggestion` | string | 否 | 可执行建议，需指明对象与方向 |
| `cost_calls` | int | 是 | 产生该记录消耗的模型调用次数（规则为 0） |
| `cost_tokens` | int | 是 | 消耗 token 数（规则为 0） |
| `dedup_group` | string | 否 | 融合簇 id |
| `rule_version` | string | 是 | 规则集或模型版本，用于结果可复现 |
| `detectors_checked` | string[] | 是 | 本单元被哪些检测器检查过，作为交叉验证广度的依据 |
| `conflict_detectors` | string[] | 否 | 明确判定不存在的检测器；非空时 `status` 必须为 `needs_review` |

**`severity` 与 `status` 必须正交。** 高严重度 + 低确定性是完全合法的组合，且是最需要提醒用户的情形：报出来，但明确标注待核实。

### 6.2 状态语义

| 状态 | 含义 | 进入报告的方式 |
|---|---|---|
| `confirmed` | 证据充分且检测器无分歧 | 计入"明确问题" |
| `probable` | 证据支持但存在不确定性 | 计入"潜在风险" |
| `needs_review` | 证据不足、检测器冲突或缺原始要求 | 计入"待人工核实" |

### 6.3 证据结构

| 字段 | 说明 |
|---|---|
| `kind` | `structural` / `visual` / `semantic` / `requirement` |
| `ref` | 证据定位，格式见下表 |
| `value` | 实测值 |
| `expected` | 期望值或阈值 |
| `note` | 补充说明，如"字体被替换为宋体" |

`ref` 的书写约定：

| kind | ref 格式 | 示例 |
|---|---|---|
| structural | `slide.{i}.shape.{shape_id}` | `slide.7.shape.23` |
| visual | `slide.{i}.region.[x,y,w,h]` | `slide.7.region.[0.12,0.55,0.30,0.20]` |
| semantic | `slide.{i}.text.{shape_id}[start:end]` 或 `pages.[i,j]` | `pages.[3,9]` |
| requirement | `prompt.cond.{cid}` | `prompt.cond.C04` |

这条约定是"可解释"落地的地方：报告里每句话都要能点回到一个 `ref`。

### 6.4 检测器原始判决（Claim）与融合

检测器**不直接产出 Finding**。每个检测器对每个「页面 × 缺陷编码 × 候选区域」产出一条 `Claim`：

| 字段 | 说明 |
|---|---|
| `detector` | 检测器标识 |
| `slide_index` / `defect_code` | 判定单元 |
| `verdict` | `present` / `absent` |
| `score` | 该检测器的原始分数（规则为 0/1，ML 为概率，LLM 为自评） |
| `bbox` | 候选区域，可空 |
| `evidence` | 支撑该判决的证据 |

设置这一层的原因有两个，都直接关系实验指标：

1. **冲突检测**：同一单元上同时存在 `present` 与 `absent` 才是真正的分歧。只记录"发现"，冲突永远无法被识别，`needs_review` 也无从触发。
2. **覆盖率统计**：实验二要回答"某方案在哪些缺陷类别上做了有效判断"。覆盖率由 `Claim` 的 `(detector, code)` 组合给出，无法从 Finding 反推。

融合后，`present` 的 Claim 转为 Finding；`absent` 不进入报告，仅参与冲突判定与覆盖率统计。

> 不同来源的 `score` 语义不同，不能直接互比。规则是布尔判决，ML 是概率，LLM 自评可能系统性偏高。跨检测器比较前必须做转换与校准，或在报告中降级为 ordinal 等级（低 / 中 / 高）。

### 6.5 融合与复核规则

**去重**：同一 `slide_index`、同一 `defect_code`、bbox IoU > 0.5 的记录归入同一簇。

**簇内定级**：
1. 严重度取簇内最高值。
2. 状态按"最保守"原则：存在任一 `needs_review` 且无 `confirmed` 时，整簇为 `needs_review`。
3. 若两个检测器对同一簇给出相反结论（一个判定存在、一个判定不存在），整簇降级为 `needs_review` 并触发复核。

**按需复核的触发条件**（这是"分层"体现智能的地方，须在代码中显式实现）：

| 触发条件 | 处理 |
|---|---|
| 检测器结论冲突 | 升级至 L3 复核一次 |
| `confidence` 落在 [0.40, 0.60] 不确定带 | 升级至 L3 复核一次 |
| 缺陷为 `blocking` 但仅单源支持 | 升级至 L3 复核一次 |
| `R-` 族缺陷但无 Prompt | 不升级，直接标 `needs_review` |

复核次数必须计数并纳入成本统计，否则"分层省钱"无法被验证。

## 7. 要求条件结构（Condition）

`R-` 族依赖把自然语言要求拆成可核验条件。条件本身也需结构化，否则无法判定"这条要求算不算满足"。

| 字段 | 说明 |
|---|---|
| `cid` | 条件编号，如 `C01` |
| `text` | 原话摘录，保留用户表述 |
| `type` | `count` / `presence` / `style` / `scope` |
| `op` | `<=` / `>=` / `==` / `in` / `contains` |
| `value` | 期望值 |
| `checkable` | `auto`（规则可判）/ `assisted`（需模型辅助）/ `manual`（无法自动核验） |

拆分要求：一句 Prompt 可拆出多条条件；`checkable = manual` 的条件必须原样呈现给用户，不得由模型代为判断，也不得计入"未满足"。

对应状态沿用四态：已满足、部分满足、未满足、待核实。

## 8. 标注规范

### 8.1 标注单元与顺序

标注单元为「页面 + 区域 + 缺陷类型」。每条标注**分三步独立完成**：

1. **存在性**：是 / 否 / 不确定（三分类，追求高一致性）
2. **严重度**：blocking / major / minor（序数，用锚点判定）
3. **定位**：bbox 或对象 id

三步分开的意义：存在性的一致率通常显著高于严重度。先冻结存在性，再讨论严重度分歧，能避免两个维度互相污染。

### 8.2 判定锚点

每类缺陷需 2 个正例、2 个边界例。锚点必须来自真实样本截图，不能凭描述想象。

实验区 3 类（`S-OVERSHOOT`、`V-WHITESPACE`、`M-CROSSPAGE`）的锚点**待样本就位后补全**，当前先用 3.3 节阈值作为临时口径。标注前必须完成锚点，否则标注员只能各自理解。功能区 6 类不进标注流程，故无需锚点。

### 8.3 不确定的处理

- 允许标"不确定"，但**不确定率必须报告**。
- 某类缺陷的不确定率超过 30%，说明该类的判定标准本身不成立，应退回修订标准，而不是让标注员硬判。
- 主观性最强的 `M-DECO-FUNC`、`V-HIERARCHY`，允许较高不确定率，但该类结论在报告中只能以 `probable` 出现。

### 8.4 一致性检验

| 项目 | 要求 |
|---|---|
| 抽样比例 | ≥ 20% 页面，双人独立标注 |
| 存在性指标 | Cohen's κ，≥ 0.60 可接受，≥ 0.80 良好 |
| 严重度指标 | 加权 κ 或 Krippendorff's α |
| 分歧处理 | 讨论 → 修订规范 → 重标分歧样本 → 记录规范版本号 |
| 版本管理 | 规范每改一次，`rule_version` 递增，旧标注需回溯确认 |

### 8.5 数据泄漏防线

SlideAudit 等公开数据可能存在同一原始页面的多个修改版本。划分训练 / 验证 / 测试集时**必须先按原始页面分组，再分组划分**，不能按单张图片随机划分。这一条在实验报告中必须写明，否则所有指标不可信。

## 10. 待核查与已知不确定项

诚实清单，不得在报告中被隐去：

1. **SlideAudit 的实际标签体系尚未核查**。本文档的类别表按设计逻辑独立构建，与公开数据集的标签映射需在核查后补一张对照表；映射不上的类别不进入监督学习实验。
2. **PresentBench 用于条件拆解的可行性未验证**。当前仅假设其 rubric 可借鉴，不作为训练数据。
3. **3.3 节全部阈值为工程经验值**，未经数据校准。
4. **`R-SCOPE` 类依赖汇报场景与时长输入**，若用户不提供则该类不可用。
5. **布局特征的提取口径未定**：可用结构特征（元素类型直方图 + 位置网格），也可用图像特征，两者不可混用，需在实验一中二选一。
6. **渲染环境未定**：PowerPoint COM、LibreOffice headless 的版式差异会影响 `S-TEXT-OVERFLOW` 与 `V-WHITESPACE` 的判定，需在同一渲染管线上完成标注与检测，否则标签与检测结果不同源。

第 6 条尤其关键：**标注所用的渲染图必须与检测所用的渲染图来自同一条管线**，否则测量的是渲染差异而非 PPT 质量。
